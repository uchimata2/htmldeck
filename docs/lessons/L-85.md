# L-85 — A version directory picked by text sort quietly selects the older install

Caught 2026-08-13 (**T-131**), while adding a second caller to a locator nobody suspected. It globs
the installed plugin's version directory and takes `sorted(...)[-1]`, with a comment explaining that
the glob is there so a pinned path cannot break silently at the next update. The glob was right and
the sort was not: **as text, `0.10.0` comes before `0.5.0`**, so the first minor bump past `9` makes
the newest install the one the locator never picks.

**Nothing would have reported it.** There was one install, so the sort had one element and every run
was correct; after the bump both tools would keep running, against older code, with no error and no
version printed anywhere. The trigger arrives from outside the repository — someone else's release —
so no edit here would ever prompt anyone to look.

**How to apply.**

1. **Sort a version by its numbers.** Split on `.` and compare integers; decide where a name that is
   not all digits goes rather than letting the comparison decide for you.
2. **Assert it against a synthetic set, not the installed one.** Three fabricated paths — `0.5.0`,
   `0.9.1`, `0.10.0` — fail today if the key is wrong. A fixture built from what is installed passes
   for as long as the defect is dormant, which is the whole of the problem (**L-78**).
3. **Suspect this wherever a path is discovered rather than declared.** Cache directories, release
   folders, dated backups: the pattern is *glob and take the last*, and it is correct only while the
   text order and the real order agree.
