# L-155 — A resolver proves an id exists, never that it is unique, so two sections numbered the same are green in both directions

Found 2026-09-02 in [T-240](../../tasks/T-240-the-evaluation-document-against-itself-and-the-code.md),
closing `PR-33`. [`EVALUATION.md`](../EVALUATION.md) carried a `### 6.3` inside section 6 and a later
`## 6.3` at the parent level, placed after `### 6.4`, so the document read 6.1, 6.2, 6.3, 6.4, 6.3, 7.
Two tasks cited the first and two the second. `refcheck.py` resolved every one of them and reported
zero dead references, because each citation named a section that exists.

- **The check that would catch this is a different check.** *Does this id resolve* and *does this id
  resolve to one thing* are not the same question, and a tool built for the first answers the second
  with a green. The lesson generalises past headings: any namespace a tool resolves by first match
  — rule ids, anchors, file names on a search path — hides its own duplicates the same way.
- **The damage is silent and inverted.** A dead pointer is loud and gets fixed. A pointer that lands
  on the wrong live target reads correctly to the checker *and* to a person who follows it and finds
  a real section there. Nothing signals that it is the other one.
- **A duplicate arrives by appending, so the fix is a number nothing will append to.** The second
  6.3 was added at the end of a section it did not belong to. Renumbering it `6.5` would have put
  the next append in the same position; a number outside the section is what stops the shape
  recurring. Which number is a citation count — here, moving the section cost 5 lines and
  renumbering the sections after it would have cost 53.
- **This is [L-147](L-147.md) at the identifier layer.** There, duplicated *data* answered for what
  it was copied from and the checkers went green. Here nothing is copied: two things claim one name,
  and the resolver returns whichever it meets first.
