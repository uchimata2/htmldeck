# L-137 — Deriving what a check reads does not derive how it reads it

A membership derived by a tool is trustworthy in exactly one respect: **which** items are in scope.
It says nothing about the **instrument** pointed at them, and the two are written in different
columns of the same table, so a correct subject beside a wrong instrument looks like a correct row.

**The subject is the half that gets checked, and that is the trap.** A derived subject can be
re-printed and compared against the tree by a command, so it attracts every check anyone writes.
An instrument is prose. Nothing re-derives it, nothing compares it against the subject it is aimed
at, and a reader scanning the table reads the half that is guaranteed right and infers the half that
is not.

**It fails worst where an item is in scope for a different reason than its neighbours.** A set
assembled by one rule — *every `.html` under `examples/`* — can be perfectly derived and still mix
two kinds of thing. The rule that gathered them cannot know that one of them answers a different
question, so the single instrument written beside the set is applied to all of it.

**Measured 2026-08-23.** `tools/docs/cycles.py` derives which files each cycle of this project's
pre-release audit reads, and it states cycle 17's subject correctly — *The shipped decks and the
blindness fixture*, five files, 1,773,568 bytes. The brief beside it read *Render each offline and
look at it. `check.py`, `audit.py`, `printgeom.py`, `glitchfree.py`*: four deck gates aimed at all
five, one of which is `examples/reference-deck-seeded-defects.html`, seeded with one defect per
evaluation dimension **on purpose**, at score 0. Run as written, the cycle would have rendered a
file built to fail and read its reds as findings. The defect was raised at cycle 0 as `PR-01`, missed
for fourteen cycles, raised a second time as `PR-66`, and closed by
[T-224](../../tasks/T-224-give-the-blindness-fixture-its-own-instrument-in-cycle-17.md) — which
changed no membership at all. The fixture's honest instrument is one command,
`tools/examples/seed_defects.py --check`, and the only question it answers is whether the file is
still derived from the reference deck rather than edited.

The cheap guard is to give the instrument a column of its own beside the subject, so that a set with
two instruments cannot be written down as if it had one. Compare **L-136**, which is the same
document failing in the other direction: a count with no membership.
