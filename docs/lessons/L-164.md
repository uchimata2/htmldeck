# L-164 — A load logged in the session is not a load in the context that does the work

Found 2026-09-14 by [T-295](../../tasks/T-295-complete-t-288s-observation-and-decide-the-move.md),
which took the observation [T-288](../../tasks/T-288-move-the-rules-that-bind-only-deck-or-release-work-under-path-scoped-rules.md)
could not take on itself.

A path-scoped rule under `.claude/rules/` had existed for twelve days when a session started. The
session's main context read the matching file twice, first in part and then whole. Nothing arrived,
and the `InstructionsLoaded` log wrote nothing. A subagent of the same session then read the same
file. The rule arrived, and the log wrote a `path_glob_match` line **under the same `session_id`**. A
rule written mid-session did the same: it reached a subagent and did not reach the main context.

**So the session is the wrong unit for this evidence.** The log line names a session and a
`prompt_id`. It does not name the context the rule went into, and a subagent is a fresh reader inside
the same session. Had the subagent's line been read as the session's, it would have licensed a move
that takes rules away from the agent doing the work.

**The log is also lossy in the other direction.** One probe whose marker the subagent reported seeing
wrote no line at all. An absence in that log proves nothing, which taskmd's T-169 had already found
under concurrent session starts.

**How to apply.** Test a context-loading mechanism in the context that will depend on it. Tie each
log line to a read that context made, by its time and its `prompt_id`, and never by `session_id`
alone. When a test can only run through a subagent, record that it measured the subagent, and do not
carry a decision that binds the main context on that evidence.
