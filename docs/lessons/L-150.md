# L-150 — A reported impossibility can be a property of the reporter's instrument

Found 2026-08-30 in [T-267](../../tasks/T-267-render-py-cannot-capture-a-decks-interactive-states.md),
building a capture path for a deck's disclosed states. The adopter record it works from
([`016`](../adopter-reports/claimai/016-render-py-cannot-capture-a-decks-interactive-states.md))
names four things such a path would need, and singles one out twice:

> **No hit-testing.** Neither route answers *is this control reachable* … Item 4 has no workaround
> at all.

It has no workaround in **their** setup, and the record says why two paragraphs earlier: *a pane
that is not displayed does not composite, so transitions freeze at their start value and
hit-testing does not work.* That is a true sentence about a preview pane. It was carried forward as
a sentence about the capability.

Measured before a line was designed, in this project's own instrument — real headless Chrome, one
throwaway probe: `document.elementFromPoint` at `#next`'s centre returns `span.chev.r`, and
`elementsFromPoint` returns the whole stack down to `section.slide`. **Hit-testing works.** The item
called *the half with no workaround* turned out to be the cheapest of the four — no mechanism at
all, six lines of probe — while `:hover`, which the record treats as merely inconvenient, is the one
that genuinely cannot be reached by any DOM write and needs the CSS rewritten.

- **A report's evidence and its conclusion have different scopes, and only the evidence travels.**
  *I could not do X* is grounded; *X cannot be done* is an inference from one instrument, and the
  instrument is usually the interesting half. Read which one you were sent.
- **The cost is not a wasted afternoon, it is the wrong shape.** Believing the sentence would have
  put the effort into working around hit-testing and left the hover rewrite — the actual hard part
  — sized as an afterthought. **A wrong impossibility mis-ranks the whole design**, and nothing
  downstream re-opens a question already answered *no*.
- **The measurement is cheaper than the reasoning about it.** One probe, one Chrome launch, under a
  minute. Any impossibility a report hands you that costs less to test than to design around gets
  tested first.

**This is the ninth consecutive batch to refuse something it was handed**, and the first to refuse a
*constraint* rather than a proposed remedy — which is the same discipline pointed one step further
back. A remedy is a hypothesis (`PRE-RELEASE-AUDIT.md` §5); so is a limit.

**What to do with it.** When a record states a capability as unavailable, re-derive it on the
instrument you will actually ship against, and write the measurement into the plan **before** the
scope is set — not into the implementation notes afterwards, where it can no longer change what
gets built. T-267's plan carries a three-row table of the record's premises with a verdict on each,
written at `planned` and not at `in_progress`, which is what made the re-ranking free.
