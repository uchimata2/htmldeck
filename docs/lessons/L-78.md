# L-78 — A self-test that asserts the state of a tracked file deadlocks the command that changes it

Caught 2026-08-13 (**T-126**), on the first shell edit after `shell.py sync` shipped. One fixture
read `sync(reference_deck) == reference_deck` — *the reference deck is already synced, so it is a
no-op*. Change one line of `shell/deck.js` and that fixture fails, the self-test refuses to report,
and **every** `shell.py` command exits 2: `check`, the sprite commands, `--set`, and `sync` itself.
The tool went down at the exact moment its whole purpose applied, and the fix it was blocking was
the one that would have made the fixture true again.

**It is L-71 one step over.** There the assertion took the reference *environment* for the
definition of correct and blocked every adopter. Here it takes the reference *state* and blocks the
maintainer. Both are the same substitution — a fact about today's repository standing in for a
property of the code — and both silence the instrument that would report it.

**How to apply.**

1. **A self-test asserts what the code does, not what the repository currently contains.** The test
   for *syncing an in-step deck changes nothing* takes a deck the test synced itself. Then it holds
   on any working tree, including one mid-edit.
2. **Ask which failures the fixture can produce.** This one fails on a stale deck (not a bug) and on
   a broken `sync` (a bug), and reports both identically. A fixture that cannot distinguish the
   thing it guards from ordinary work is measuring the wrong thing.
3. **The state was worth asserting — by a gate, not a self-test.** `check_all.py` runs `shell.py
   check` over every tracked deck, which fails a release when one is behind and does not stop
   anybody from fixing it. Same fact, right instrument, and it was already there.
4. **Refusing to report on a failed self-test stays right** (**L-04**). The lesson is about what the
   fixtures may assert, never about softening the refusal.

**A second tool had it the same afternoon, which is why this is a lesson and not a bug report.**
`figures.py` seeds a fixture over the *correct* value of a figure in `examples/README.md`; when that
page has drifted the string is not there, nothing is seeded, and the tool exits saying the tool is
wrong — while the drift it exists to catch sits in the failure message
([T-127](../../tasks/T-127-figures-py-refuses-to-report-a-drifted-figure-because-its-fixture-needs-an-undrifted-page.md)).
Different mechanism, same substitution: one asserted the state, the other built a fixture out of it.
**When auditing for this, the question is not "does a fixture compare against the repository" but
"does any fixture stop working when a tracked file legitimately changes".**
