# Task workflow — htmldeck

How a task file is written, moved and closed. Mechanics only.

The *rules of the project* are in [`../CLAUDE.md`](../CLAUDE.md). *What to build and why* is in
[`../docs/BRIEF.md`](../docs/BRIEF.md). The reusable lessons behind several of the conventions
below are in [`../docs/LESSONS.md`](../docs/LESSONS.md), cited as **L-nn**. None of that is
restated here.

This file is also the specification `tools/tasks/task.py` enforces: where the two disagree, one
of them is a bug — fix it, do not work around it.

---

## 1. What a task is

**No work without a task file** — that is CLAUDE.md's rule, not this file's. One file per task in
`tasks/`, created from [`_templates/task-template.md`](_templates/task-template.md), or from
[`_templates/audit-umbrella-template.md`](_templates/audit-umbrella-template.md) when the task is
a review that will raise child fixes.

Name the file `T-NNN-<slug of the title>.md` — lower case, hyphenated, truncated where it gets
silly. The filename is a convenience; `id:` is the identity, and the tooling reads only the
front-matter. The next free number is at the bottom of [`README.md`](README.md), regenerated by
`task.py index`.

**The front-matter is the only place a fact about a task is stored.** Child lists, "blocks" lists
and the index are computed from it. A stored copy of a derivable fact drifts; a derived one
cannot (**L-08**).

---

## 2. The lifecycle

`specify → plan → implement → review`. The four numbered sections of the template are the four
phases, in order. `phase:` says which section is being worked; `status:` says which gate has been
passed.

| Phase | Section | Complete when | Status it earns |
| :--- | :--- | :--- | :--- |
| `specify` | 1. Specify | Outcome, scope in *and* out, inputs, and acceptance criteria are written and accepted. Open questions raised, with who answers each. | `specified` |
| `plan` | 2. Plan | The steps table is filled, every step naming its output. Approach decisions recorded with their rationale. | `planned` |
| `implement` | 3. Implement | The outputs exist on disk. Decisions and assumptions written down as they are taken, not reconstructed afterwards. | `in_progress` throughout |
| `review` | 4. Review | Every acceptance criterion has a verdict and a note pointing at the evidence. Child fix tasks raised or "none". | `done` |

Three rules that are not obvious from the template:

- **Acceptance criteria are written before the work, not after it.** A criterion invented at
  review time is a description of what happened.
- **`not met` is a legitimate way to close.** A criterion recorded as unmet, with a reason and a
  gap or child task raised against it, closes a task honestly. A criterion quietly reworded to
  match the output does not.
- **Verify against the real case, and look at what was produced** (**L-01**, **L-02**). For
  anything that renders, CLAUDE.md sets the bar: a task is `done` only when its deliverables
  exist, its log is current, and any deck it produced has been opened and looked at, offline.

## 3. The front-matter schema

Every field below appears in every task file. Order is conventional, not enforced.

| Field | Form | Notes |
| :--- | :--- | :--- |
| `id` | `T-NNN` | The identity. Must match the file it sits in and be unique. |
| `title` | One line, imperative | Appears in every generated view, so it has to read out of context. |
| `type` | `analysis` · `decision` · `deliverable` · `research` · `fix` · `admin` · `audit` | Classification only; not enforced by `check`. |
| `status` | See §3.1 | Enforced. |
| `phase` | `specify` · `plan` · `implement` · `review` | Enforced. |
| `parent` | `T-NNN` or `null` | See §4. |
| `blocked_by` | `[T-NNN, T-NNN]` or `[]` | See §4. |
| `related` | `[T-NNN]` or `[]` | See §4. |
| `decisions` | `[D-NNN]` or omitted | Optional. See §4. |
| `work_package` | `WP1` … `WPn` · `final` · `none` | Groups the index. |
| `owner` | A role, e.g. `maintainer` | Who decides, not who types. |
| `created`, `updated` | `YYYY-MM-DD` | `updated` is the date shown in the closed table. |
| `deliverables` | `[path, path]`, a block list, or `[]` | Repo-relative paths. `task.py deliverables` reports which of them exist yet. **This field is the only place an unproduced output is written as a path** — front-matter is not pointer-scanned, prose is. In §2 and §3, name a not-yet-existing output rather than pointing at it (`` `R7-printable-mode.md`, under `docs/research/` ``), or `check` reports it as a dead pointer, correctly. |

**Never write `children:` or `blocks:`.** Both are derived from the edges below, and `check`
rejects a task file that still carries `children:`.

### 3.1 Status vocabulary

Eight values. Anything else is a typo, and `check` says which task has it.

| Status | Means | Usual phase |
| :--- | :--- | :--- |
| `proposed` | The file exists; the spec is not agreed yet. | `specify` |
| `specified` | §1 is complete and accepted. Ready to plan. | `specify` |
| `planned` | §2 is complete. Work can start. | `plan` |
| `in_progress` | Being worked. | `implement` |
| `blocked` | Cannot proceed. Requires a non-empty `blocked_by` — `check` enforces that pairing. | any |
| `review` | The outputs exist; verdicts are being written. | `review` |
| `done` | Closed, at CLAUDE.md's bar for done. | `review` |
| `cancelled` | Closed without the work. The log must say why. | any |

`done` and `cancelled` are the closed statuses. Everything else counts as **open**, which is what
the index splits on and what decides whether a blocker still gates its downstream tasks.

## 4. Which edge to use

Four edges are stored. Pick by what the edge should *do*, not by how related the two tasks feel.

| Edge | Use it when | Derived counterpart |
| :--- | :--- | :--- |
| `parent` | This task exists because of that one — a fix raised by an audit umbrella, a split of a task that turned out to be two. | `children` on the parent |
| `blocked_by` | That task must land before this one can start. **The only edge that gates.** | `blocks` on the upstream task |
| `related` | Read that for context. Explicitly not a gate. | — |
| `decisions` | An open question in `tasks/DECISIONS.md` that this task is waiting on. Each `D-NNN` must have a row there. The register is created the first time a task needs one; until then, absent is correct. | The decision's "blocks" list |

- **`blocked_by` is expensive.** It stops work and it propagates. Use it for a genuine gate;
  `related` costs nothing and carries most of the value.
- **No cycles.** A blocks B blocks A deadlocks the backlog silently, so `check` walks the graph
  and reports any loop.
- **Every reference must resolve.** A `parent`, `blocked_by`, `related` or `decisions` entry
  pointing at something that does not exist is a `check` failure (**L-09**).

## 5. The log

The table at the bottom of every task file. **One row per status change**, with a note saying
what changed and why — not that it changed.

The generated views tell you where a task is. The log is the only record of how it got there, and
it is the first thing a later session reads. Where direction changed without a status change,
write a `(no change)` row for it.

## 6. The tooling

```
python tools/tasks/task.py context T-NNN    # everything needed to start one task
python tools/tasks/task.py index            # regenerate the tables in tasks/README.md
python tools/tasks/task.py check            # validate
python tools/tasks/task.py check --closing  # stricter: a leftover working file becomes a failure
python tools/tasks/task.py decisions        # open decisions and what each is holding up
python tools/tasks/task.py deliverables     # every declared output, and whether it exists
```

`index` rewrites only the block between its generated markers; hand-written sections of
`README.md` survive it.

**Generated views count only open tasks as gated.** Both directions of an edge are filtered the
same way: a closed task neither gates anything nor waits on anything, so it is absent from a
*Blocked by* column, a *Blocks* column, and a decision's "blocks" list. The two views then differ
on purpose, and only in what they do with the closed ones:

| View | Read to | Closed tasks on an edge |
| :--- | :--- | :--- |
| `index` (the board) | **choose** what to work on | Dropped. The board has no column for a status, and a closed downstream task overstates how much a row unblocks. |
| `context` | **do** one task | Kept, with their status and marked as not waiting. They are the trail explaining why the task exists. |

Stated here because it was previously implied by two comprehensions that disagreed with each
other, which is how it survived being read repeatedly (**T-031**, **L-08**).

**What `check` enforces**

- `status` and `phase` are in the vocabularies in §3.
- No `children:` field.
- Every `parent`, `blocked_by`, `related` and `decisions` reference resolves.
- `blocked` implies a non-empty `blocked_by`.
- No dependency cycles.
- Every markdown link, and every repo-relative `.md` path written in prose or printed by a tool,
  resolves in a fresh clone. **Two things are skipped, and `check` prints how many:** documents
  `.gitignore` excludes, which are machine-local by design and absent from the clone; and
  **front-matter, which is a structured record rather than prose** — so `deliverables:` can name
  an output that does not exist yet without that counting as a broken pointer.
- **There is no exemption for declared deliverables.** Until T-029 there was: any path a task
  named in `deliverables:` was skipped *everywhere in the repository*, on the reasoning that a
  deliverable is a promise about the future. It was hiding **110 of 357 pointers**, because most
  declared outputs are long-existing documents that everything else cites. Declaring one existing
  file added six more to that total and `check` still reported `0 broken` (**L-05**).
- With `--closing`, `deliverables/_working/` is empty.

**What it does not.** `check` validates structure and references. It cannot tell you a
specification is wrong, a plan is thin, or a deliverable is bad — and it says so in its own
output rather than reporting a clean pass (**L-05**).

## 7. The two checklists

**Opening a task**

1. Copy the template, take the next ID from `README.md`, name the file after the title.
2. Fill §1 and the front-matter. Set `related` and `blocked_by` deliberately; default to
   `related`.
3. `python tools/tasks/task.py index` — the task appears in the tables.
4. `python tools/tasks/task.py check` — it passes before any work starts.

**Closing a task**

1. Every acceptance criterion has a verdict and a note in §4.
2. Every deliverable exists at the path the front-matter declares —
   `python tools/tasks/task.py deliverables` confirms it.
3. Anything the task produced that renders has been opened and looked at, offline.
4. Findings worth keeping beyond this task are in [`../docs/LESSONS.md`](../docs/LESSONS.md),
   not only in the task file.
5. `status: done`, `updated:` today, a final log row.
6. `python tools/tasks/task.py index && python tools/tasks/task.py check --closing`.
